# mobx-view-model и mobx-tanstack-query для приложения тренировок

Дата проверки: 2026-11-05. Статус: исследование кандидатов, не решение о внедрении. Проверены официальная документация, исходники и содержимое тестов; зависимости не устанавливались, тесты библиотек не запускались. Проверка исходников не доказывает работоспособность будущей комбинации зависимостей приложения.

Последующее решение владельца: для MVP выбран официальный `@tanstack/react-query`, `mobx-tanstack-query` отложен. Использование `mobx-view-model` и `mobx-view-model-react` отдельно не утверждено. Актуальное решение записано в [ADR 0005](../adr/0005-server-state-and-workout-draft.md); ниже сохранены результаты исследования и рассмотренные альтернативы.

## Контекст и вывод

Уже приняты [ADR 0005](../adr/0005-server-state-and-workout-draft.md): серверные данные принадлежат TanStack Query, локальный черновик тренировки и UI — MobX; и [ADR 0006](../adr/0006-feod-for-frontend.md): frontend организуется по FEOD. Офлайн-запись и последовательный переход между устройствами описаны в [ADR 0003](../adr/0003-offline-workouts-and-device-handoff.md). На момент исследования дополнительные библиотеки ещё не были выбраны.

Рекомендация исследователя: `mobx-view-model` можно рассматривать для жизненного цикла моделей экранов. `mobx-tanstack-query` имеет смысл, если запросами действительно удобно управлять из этих моделей: он сохраняет TanStack Query владельцем кеша, но добавляет второй механизм наблюдения и особенности очистки. Для небольшого React-приложения исходный вариант с официальными React Query hooks и обычными MobX-моделями остаётся проще; сами авторы адаптера рекомендуют React-проектам официальный `@tanstack/react-query`. Это рекомендация, а не изменение принятого стека. [Официальное руководство адаптера](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/docs/introduction/getting-started.md).

## mobx-view-model: что подтверждено

- **Разделение пакетов.** `ViewModelBase`, store и конфигурация находятся в `mobx-view-model`; `useCreateViewModel`, HOC и provider — в отдельном `mobx-view-model-react`. Для hook-варианта компонент оборачивается в `observer` из `mobx-react-lite`. Глобальный `ViewModelStore` в руководстве необязателен. Старые примеры импортов нельзя переносить без проверки версии. [Интеграция React](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/docs/react/integration.md).
- **Жизненный цикл.** `mount()` вызывает `willMount()`, ожидает возвращённый Promise и затем завершает mount через `didMount()`; unmount вызывает `willUnmount()` и `didUnmount()`, затем abort контроллера. `unmountSignal` позволяет привязать MobX reactions и прочие ресурсы к mount-циклу. Автоматической очистки произвольных ресурсов без такого связывания нет. При повторном mount базовый класс заменяет уже отменённый сигнал новым. [Исходник lifecycle](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/packages/core/src/view-model/view-model.base.ts#L136-L220), [документированный пример autorun с signal](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/docs/api/view-models/base-implementation.md#unmountsignal).
- **React commit и cleanup.** Hook создаёт/находит VM, запускает клиентский mount в commit effect и освобождает VM через `releaseVm` при cleanup; внутри есть отдельная обработка staged/unconfirmed экземпляров. Создание VM и завершённый mount нельзя считать одним моментом: первоначальный render может видеть `isMounted === false`. [Hook](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/packages/react/src/hooks/use-create-view-model.ts), [описание интеграции](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/docs/react/integration.md).

Практическое следствие: модель страницы может исчезнуть при навигации, а активная тренировка должна сохраняться. Черновик следует держать в предметном модуле с отдельным владельцем времени жизни и долговременным сохранением, передавая модели экрана доступ к нему. Одноразовые query wrappers/reactions, привязанные к старому `unmountSignal`, при реальном remount нужно создавать заново, а не ожидать, что новый сигнал воскресит отменённый объект. Это вывод из lifecycle, а не готовая функция библиотеки. [Lifecycle source](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/packages/core/src/view-model/view-model.base.ts#L143-L220).

## mobx-tanstack-query: кеш и совместимость

Заявление README об обёртке над Query Core подтверждено исходниками. Экспортируемый `QueryClient` наследует core-клиент, добавляя hooks и defaults адаптера. Тип `AnyQueryClient` явно принимает как расширенный клиент, так и обычный core-клиент. `Query` создаёт настоящий `QueryObserver` с переданным клиентом. Следовательно, второй клиент для MobX не требуется: одна ссылка на QueryClient может обслуживать React Query, модели и router loaders. Это архитектурная совместимость по исходникам; интеграция с конкретной установленной версией React Query ещё не проверялась. [QueryClient](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/query-client.ts), [типы](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/query-client.types.ts), [создание observer](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/query.ts#L285-L359).

Обёртка хранит observable-снимок результата observer (`_result`), по умолчанию через `observable.ref`; `updateResult()` присваивает результат observer, а `setData()` делегирует `queryClient.setQueryData()`. Отдельного полного кеша сущностей в MobX здесь нет. Однако `resultObservable` настраивается: для выбранной границы ответственности стоит сохранить `ref`, читать серверные DTO как immutable и не превращать их в редактируемый черновик. Черновик — явно созданная локальная модель, которую фоновый refetch не перезаписывает. [BaseQuery initialization](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L114-L176), [setData](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L287-L300), [updateResult](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L398-L406).

Настройки отличаются от привычных React Query defaults: wrapper подставляет `structuralSharing: false`, если значение не задано, и `notifyOnChangeProps: 'all'`. Это нужно учитывать при оценке перерисовок и ссылочной стабильности данных. Присутствуют оба overload конструктора — объект конфигурации и `(queryClient, () => options)`; последний не обязательно означает устаревший пример. [Конструктор Query](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/query.ts#L242-L359).

Для проекта предпочтительно явно передавать общий клиент. В `preset` есть собственный singleton и автоматический mount; их слепое использование способно нарушить выбранное владение клиентом. Обычный `new Query(...)` сам не управляет mount/unmount клиента. В React этим занимается `QueryClientProvider`; при другом владельце приложения lifecycle клиента нужно организовать явно. [Preset singleton](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/preset/query-client.ts), [preset factory](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/preset/create-query.ts#L110-L120), [QueryClientProvider](https://tanstack.com/query/latest/docs/framework/react/reference/functions/QueryClientProvider).

## Очистка, mutations и риски интеграции

`Destroyable` связывает собственный AbortController с внешним `abortSignal`; `destroy()` отменяет внутренний сигнал и вызывает cleanup. Query cleanup отписывается от observer, очищает listeners и вызывает `queryObserver.destroy()`. По умолчанию удалять общий кеш при уходе с экрана не требуется; `resetOnDestroy` сбрасывает данные, а `removeOnDestroy` действительно вызывает `removeQueries`. Вариант `'safe'` проверяет наличие других observers, но всё равно удаляет запись, когда их нет. Для сохранения кеша между экранами эти опции следует оставить выключенными. [Destroyable](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/utils/destroyable.ts), [cleanup](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L556-L582), [remove](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L480-L513).

Отдельный риск по исходникам, без runtime-воспроизведения: eager reaction динамических options получает **внешний** `params.abortSignal`, а её disposer не сохраняется для `cleanup()`. При одном `query.destroy()` внешний сигнал может оставаться активным. При этом `update()` проверяет внутренний aborted-сигнал и немедленно возвращается: утверждать, что после destroy продолжаются сетевые запросы, оснований нет. Риск относится к освобождению reaction/замыкания. Lazy-ветка содержит disposer через `onEnd`, что не доказывает очистку eager-ветки. В проверенной версии нет отдельного `initTracking`: логика находится в `finalizeInitialization`. Безопасный для первой интеграции контракт — создавать per-mount wrapper с явным сигналом владельца и завершать именно этот сигнал; первый тест должен проверить отсутствие дальнейших вычислений динамических options после завершения владельца. [Eager/lazy tracking](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L188-L245), [guard update](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L320-L339), [cleanup](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/base-query.ts#L556-L582).

`Mutation` построен на core `MutationObserver`, поддерживает callbacks/инвалидацию и передаёт собственный signal в контекст `mutationFn`. При destroy снимается подписка и очищаются listeners. Передача signal не отменяет HTTP-запрос автоматически: транспорт должен использовать его, а уже принятый сервером результат не откатывается. Отправку результатов активной тренировки поэтому нельзя безусловно привязать к уходу со страницы; ей нужен владелец времени жизни операции синхронизации. [Mutation constructor и mutate](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/mutation.ts#L150-L332), [cleanup](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/mutation.ts#L400-L423).

## Что есть в тестах, а что ещё проверить

Исходники VM содержат тесты lifecycle и abort, React StrictMode, Suspense и abandoned renders. Однако конкретный core-тест повторного mount с заменой `unmountSignal` помечен `it.skip`; нельзя приводить его как прошедшее доказательство. Query содержит тесты реактивных options, cache invalidation, destroy/reset/remove; mutations — тест передачи abort-сигнала и однократной инвалидации. Само наличие тестов полезно, но результаты их запуска и CI здесь не проверялись. [Core tests](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/packages/core/src/view-model/view-model.base.test.ts#L271-L327), [StrictMode tests](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/packages/react/src/hooks/strict-mode-vm.test.tsx), [Suspense tests](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/packages/react/src/hooks/suspense-lazy-duplicate-vm.test.tsx), [Query tests](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/query.test.ts), [Mutation tests](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/src/mutation.test.ts).

До внедрения достаточно одного небольшого интеграционного сценария на зафиксированных зависимостях: React Query hook и MobX Query видят обновления одной записи общего QueryClient; уход со страницы освобождает observer и options reactions; StrictMode/remount не дублирует операции; фоновый refetch не теряет введённый подход; операция сохранения переживает навигацию согласно выбранному владельцу. Отдельный офлайн-сценарий должен проверить перезагрузку с неотправленным подходом, повторную отправку и отсутствие дубликатов — это уже проверка протокола приложения.

## Offline, persistence, routing и FEOD

Эти библиотеки не выполняют ADR 0003 автоматически. VM lifecycle не является долговременным хранилищем. Документация query-адаптера предлагает подключать persister из TanStack отдельно; официальный TanStack требует согласовать `gcTime`/`maxAge`, восстановление и, для продолжения persisted mutations после reload, зарегистрировать default mutation function. Ни этот механизм, ни MobX не определяют идентификаторы операций, защиту от дубликатов или устаревших записей со второго устройства. Они остаются отдельным проектированием приложения. [Документация persistence адаптера](https://github.com/js2me/mobx-tanstack-query/blob/390277d3b7e3810f0b4811a7f6e3c577be40b8d6/docs/api/QueryClient.md#persistence), [TanStack persistence](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient), [TanStack persisted mutations](https://tanstack.com/query/latest/docs/framework/react/guides/mutations#persisting-offline-mutations).

Рекомендация размещения в рамках принятого FEOD: общий QueryClient, providers и связывание TanStack Router — в сборке `app`; тонкие страницы получают route-параметры и создают модели экрана; предметный модуль владеет черновиком активной тренировки и его публичным API; общие низкоуровневые адаптеры выносятся в `common` только при реальном повторном использовании. Библиотеки не устанавливают правила FEOD, не задают маршруты и не требуют отдельного глобального каталога всех view models. Точные пути определяются при создании frontend и профиля FEOD, не этим исследованием. [ADR 0006](../adr/0006-feod-for-frontend.md), [React integration и optional store](https://github.com/js2me/mobx-view-model/blob/743d08bbb2ee4c3b7bb07bf615d3c9587ab26ae0/docs/react/integration.md).
